### T-18: the filed root cause was wrong

The docket's original T-18 entry concluded "stale on-disk copy that `validateConfigVersion` never regenerates". That is
not what is happening on this server, and the correction is recorded on docket line 18 (now P2):

- **There is no on-disk copy at all.** `plugins/Gangland_Warfare/message/` does not exist, and
  `find . -name "message_*.yml"` over the whole server tree returns nothing — after eight fresh boots.
- **That absence is by design**, per Keystone's own `LanguageLoader` javadoc: *"disk-absent files load from the bundled
  jar resource in memory only — no disk copy — so admins never end up with a surprise file they didn't create."*
  So the loader was reading the jar, and the warning is correct about the jar.
- **The jar's own YAML shadows the key.** Inside the single `Errors:` block (line 447) of `message/message_en.yml`,
  `Bounty:` is declared **twice** — line 471 (carrying `Below_Minimum`, added by commit `61d45ddc`) and line 494
  (carrying `No_Bounty` / `User_Set_Bounty`). SnakeYAML keeps the last duplicate mapping key, so `Errors.Bounty`
  resolves to the line-494 block and `Below_Minimum` genuinely is not in the parsed config.
- **`message_es.yml` has the identical defect** — `Errors:` at 345, `Bounty:` at 369 (with `Below_Minimum` at 370) and
  again at 392.

This also explains the observed symptom exactly: `Messages.BOUNTY_BELOW_MINIMUM` falls back to its enum default, which
is what the original T-18 observation reported.

## 4. Harness defects found and fixed

Fixed in `smoke/smoke.py` and `smoke/scenarios.json` (test tooling only — no plugin source was touched).

| # | Defect | Fix |
|---|---|---|
| H1 | **S7 asserted a fault id that does not exist.** `scenarios.json` expected `module.host_api`; Keystone's real constant is `ModuleResolution.FAULT_HOST_INCOMPATIBLE = "module.host.incompatible"`. It also expected the literal `Host_Api`, which never appears in the emitted line — `report()` logs `[{code}] {message} {context}` and the message reads "was built for host 0.7 but the host is 0.8". | Expect `module.host.incompatible` and `was built for host 0.7`. |
| H2 | **S7 could never reach the host-api check.** The variant jar kept the source jar's `Id: weapon`, so `ModuleResolution.resolve()` — which applies `module.duplicate` (rule 1) *before* `module.host.incompatible` (rule 2) — dropped it as a duplicate of the real weapon jar (equal versions ⇒ the later-discovered jar loses). The row would have asserted a fault the loader could not emit. | Added an optional `id_override` to `make_hostapi_variant()` (and an `extra_module_jars` key for it) so both descriptors survive rule 1 and rule 2 is the one that rejects the variant. Confirmed by the S7 log line in §1. |
| H3 | **Six rows asserted `onDisabled`, a string a healthy shutdown can never produce.** Keystone mentions `onDisabled` only inside the `FAULT_DISABLE_FAILED` message, and no module logs anything in its own `onDisabled()`. The rows were asserting a *failure* string. | Replaced with `Disabling Gangland_Warfare`, which the disable path really emits. |

Fixed by the orchestrator during S4/S5: the module id is `copsncrooks`, not `cops` (the `modules` key is a
deploy-side jar selector, the `loaded_modules` expectation is the real `module.yml` `Id`), and PlaceholderAPI's
anti-malware download ERROR needed allowing in `no_errors_except` as third-party noise.

**Not a defect, but a real observability gap:** no module logs anything on disable, and Keystone logs a module's
`onDisabled` only when it *throws*. The board's "`onDisabled` per module" expectation therefore has no console
evidence available to it. A one-line `log.info` per module unload (mirroring `Loaded module <id>`) would make the
shutdown half of every future matrix row assertable; today it is only verifiable by the *absence* of a fault.

## 5. In-game checks left for the user

Everything below needs a player and cannot be reached from the console — `/glw weapon list`, `/glw car` and friends all
answer `Error: You need to be a player to use this!`. The matrix proves these commands *resolve and dispatch*; it proves
nothing about what they do.

- **Weapons** — fire each of the five action types (gun, incendiary, biological, melee, throwable), not just a rifle;
  check ammo consumption, reload, and that `SINGLE`/`BURST` are one click per shot/burst while only `AUTO` holds to fire.
- **Recoil feel** — the NMS recoil adapters are per-revision; confirm the recoil actually applies on 1.21.11 and does not
  look wrong or absent.
- **Cops** — cop spawn from a spawner, pursuit, and arrest/detainment end to end; confirm the detainment table really
  migrated (S4's "detainment table migrates" is a database fact with no console line, so the matrix could not check it).
- **Trader and banker menus** — especially **the AnvilGUI rename views** (`BankerEditNameCommand`,
  `TraderEditNameCommand`, `BankerRenameAccountView`, `BankerCreateAccountView`, `BankerAmountView`,
  `QuantitySelectorView`). These are the exact classes T-12's `NoClassDefFoundError` came from. Boot no longer crashes,
  but the fix removed a shade *relocation* — only opening one of these views proves AnvilGUI resolves at runtime.
- **`/glw car`** — spawn and drive a car; refuel a parked car and watch for the missing `maxFuel` clamp (docket line 3).
- **Jetpack** — equip, fly, fuel drain.
- **Turf** — capture a turf with garrison NPCs present, contribution accrual, and the turf powerup NPC
  (`/glw turf powerupnpc`).
- **`/glw reload` mid-play** — with players online and a car/jetpack/weapon in hand. S8 proves the reload path is clean
  on an empty server; it says nothing about live sessions.
- **Loot chests** — worth a look given docket line 11 (P1): `loot_chests.yml` carries 44 `weapon:`, 12 `wearable:` and
  29 `ammo:` refs resolved by a module bean with no ordering edge to `GameplayConfig.lootChestLoader`. Open several
  chests and confirm weapon/wearable/ammo drops actually appear.
