## Data flow in one paragraph
Wanted start/end/level events (`CopListener.java:41/51/62/74`) call `CopManager.onWantedStart/End/LevelChange`. Start creates the player's `CopGroup` (owns one Keystone
`NpcSquad`; `CopManager.newGroup` :394 installs `CopRadio.listenerFor`), seeds the squad with the player's location, dispatches, and starts two per-player BukkitTasks:
spawn task (`Spawn_Check_Rate`, first run +20t) -> `spawnTick`, AI task (`AI_Tick_Rate`, first run 0t) -> `aiTick`. aiTick ticks every cop (`CopNpc.tick(target)` -> state
behaviour), then field care, then the resisting poll, then drains queued radio calls. Squad signals (CONTACT, MAN_DOWN ...) reach the `CopRadio` listener synchronously inside
Keystone; the listener speaks lines, queues a `RadioCall` (answered after the cop loop) and may grant backup.

## Spec drift (SPEC-0.15.md vs today's code)
1. `CopRadio.listenerFor` is at CopRadio.java:90-107, not 79-91 (spec line 241). `CopGroup.fallBackUntil :70`, `isFallingBack :144`, `requestBackup :149` are exact.
2. Spec f-regroup says Regroup "set fallBackUntil (up to 15 s)" as if extending a mechanism; today only a dead Commander sets it (fixed `COMMANDER_FALL_BACK_MS = 5_000`, CopRadio:58) and it ends purely on the clock.
