### C1 (Critical) — a detour left the flow adopting into a closed inventory
`suspend()`/`resume()` ported Oriel's flag only; Gangland's `MultiPanelInventory.suspend()` nulled its live handle
for exactly this reason — an external inventory (AnvilGUI, a chat prompt) Bukkit-closes the player's current
window, but `currentMenu` here still pointed at that now-closed `ChestMenu`. `resume(); switchTo(samePanel)`
(the `ShopAdminView.java:426-429` pattern) went through `rerender()`'s in-place `adoptComponentsFrom` path,
writing fresh components into an inventory nobody could see; the different-panel case hit `switchInternal`'s
own in-place branch for the same reason. Player left with no window and a live, still-tracked flow.

**Fix:** new `private boolean detoured` field, set by `suspend()` alongside the existing `suspended` flag; both
`rerender()`'s row-count check and `switchInternal`'s in-place-switch condition now also require `!detoured`,
forcing the full close+reopen path while set; `detoured` clears only once that full-reopen branch actually runs
(`newMenu.open(viewer)`), not in `resume()` — `resume()` alone doesn't re-establish a real window, only a
subsequent switch/rerender does. `currentMenu.close(viewer, CloseReason.NAVIGATION)` in the reopen branch is
harmless even when the inventory is already Bukkit-closed (it just untracks + drains held items).

Per W30's note, this bug exists in Oriel's own shipped `chest/flow/MenuFlow.java:184-192` too — flagged as a
docket candidate (OR-) below, not fixed here (out of this stream's scope).

### I2 — `MenuFlow` hard-coded `ChestMenu.builder(service)`, blocking Oriel's rebase
`Panel.render` takes a bare `ChestMenuBuilder`, and all three of `MenuFlow`'s own `ChestMenu.builder(service)`
call sites (`rerender()`, `switchInternal`'s in-place branch, `switchInternal`'s reopen branch) constructed the
base builder directly — a product subclassing the whole stack (a `ChestMenu` subclass + `ChestMenuBuilder`
subclass, per E6.1's F5 extension points) had no way to make `MenuFlow` drive its own type, meaning Oriel's
rebase could not actually delete its own `chest/flow` and reuse this one (`docs/extraction-roadmap.md:466`'s own
stated goal).

**Fix (additive, per W30 — cheaper now than after Oriel's rebase lands):** new
`MenuFlowBuilder.menuBuilder(Supplier<ChestMenuBuilder>)`, defaulting to `() -> ChestMenu.builder(service)`;
`MenuFlow`'s constructor now takes the resolved `Supplier<ChestMenuBuilder>` and all three call sites use
`menuBuilderFactory.get()` instead of the hard-coded call.

### I4 — an ended flow could register a second `FlowCloseListener`
`end()` guards against a second call via `if (ended) return;`, but `openAt()` had no equivalent guard — calling
it again after `end()` (e.g. a double-click on some "open shop" trigger racing with the flow's own natural close)
registered a second listener that leaked forever (the first was already unregistered by `end()`, but nothing
stopped a second one from being added).

**Fix:** `openAt()` now starts with `if (ended) return;`.

### M1 — the back-stack was unbounded
`NavigationHistory` (the tracker-level "back" trail) bounds itself at `MAX_DEPTH` (32); `MenuFlow`'s own
`backStack` — a separate, flow-scoped back-stack — did not. **Fix:** `switchTo`'s push now trims from the tail
(`backStack.removeLast()`) while `backStack.size() > NavigationHistory.MAX_DEPTH`, matching `NavigationHistory`'s
own cap and reusing its constant rather than duplicating the number.

### M2 — no end-to-end test for stale-slot clearing across a page change
Not a bug — `ChestMenu.adoptComponentsFrom` (from E6.1) already correctly clears a slot that existed on the
outgoing component set but not the incoming one, which is exactly what happens when a `MenuFlow.rerender()`
re-invokes a `Panel.render()` that calls `PagedRegion.render` with a shorter page. This was simply never pinned
end-to-end. New test: page 0 (7 entries, region fully occupied) → `rerender()` to page 1 (3 entries) → assert the
3 occupied cells render and the 4 now-unoccupied trailing cells read `null` (no leftover item from page 0).

### M3 — `PagedRegion.render` never validated the config against the actual builder
A `PageConfig` built assuming one menu size (e.g. 6 rows) used against a `ChestMenuBuilder` actually configured
for a smaller one (e.g. 3 rows) would previously just skip most of the mismatch silently rather than fail loudly.
**Fix:** new `public int rows()` getter on `ChestMenuBuilder` (the smallest surface `PagedRegion` needs from a
different package); `PagedRegion.render` now throws `IllegalArgumentException` up front when
`config.lastRow() >= builder.rows()`.
