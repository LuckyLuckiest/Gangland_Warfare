## Deviations from the plan
1. **`ChestClickContext`/`ChestRenderContext`/`ChestSlotView`/`PassthroughPlaceholders` land in
   `inventory.chest`, not `inventory.chest.internal`.** The E6.1 table says "package-private" for these three.
   Java package-private access does not cross a sub-package boundary, and `ChestMenu` (which must construct all
   three on every render/click pass) needs direct access — so making them literally package-private only works if
   they're co-located with `ChestMenu` in the same package. I judged the literal "package-private" instruction as
   binding over the literal "`inventory.chest.internal`" path notation, since the former is a stated design
   requirement (tighter encapsulation than Oriel, which made its equivalents `public`) and the latter reads as
   shorthand, not a hard path contract. Each class's javadoc says so.
2. **No `ChestLifecycleClickContext`.** Oriel uses a dedicated headless-context class to dispatch `on_open`/
   `on_close` handlers (no real click event). `ChestClickContext` already tolerates a `null` event and any slot
   value (its `cancel()` no-ops if `event == null`), so I reused it with `slot = -1` and `event = null` instead of
   porting a second class for the same shape — ponytail: already in the codebase, reuse it.
3. **`ChestMenuBuilder.vetoClose(Predicate<Player>)` is new, not a straight port.** The E6.1 table lists
   `vetoClose` among the builder's methods, but Oriel's only close-veto path is its `RequirementHook`-based
   `closeRequirement` — explicitly one of the "deliberately not ported" advanced features (fail-action chains,
   `RequirementSet`). I added a plain-predicate `vetoClose`/`ChestMenu.closeVeto` as the basic-mechanism
   counterpart: `MenuTarget.vetoesClose(Player)` now has a real (if minimal) implementation in the base class
   instead of always returning the interface default `false`. Oriel's subclass overrides `vetoesClose` with its
   own requirement-hook logic instead of using this field.
4. **`close(player, reason)` does not special-case `USER`.** Oriel's current `close(Player, CloseReason)` returns
   held items for every reason including `USER`, with a `skipIfSlotEmpty` guard against double-issuing (a fix
   from its own commit history). In production Oriel code that overload is *never actually invoked* with
   `CloseReason.USER` — a genuine Escape-press never reaches it at all (it goes through the close listener's
   `returnHeldItemsOnUserClose`, which isn't part of the E6.1 `MenuTarget` surface). Since Keystone's base
   `ChestMenu` has no such second path, `close(player, reason)` unconditionally returns held items for whatever
   reason is passed and drops the `skipIfSlotEmpty` guard — there is no live-click race to guard against on this
   path. Matches the gate's literal scope ("closeAll returns held items on RELOAD/PLUGIN_DISABLE"); documented as
   a known gap in `ChestMenu.close(Player, CloseReason)`'s javadoc for Oriel's rebase to fill if its own subclass
   needs Escape-press item return.
5. **`ChestMenu.builder(InventoryService)` only — no service-less overload.** Oriel's `builder()`
   (no-arg) relies on the static `MenuTracking` no-op fallback. Keystone has no static tracker (by design — the
   shared-classloader constraint), and `MenuHolder`'s constructor requires a real `InventoryService` for identity,
   so every menu needs one. This falls directly out of the plan's own "no static tracker" decision; flagging it
   because it's a visible API-shape difference a caller will hit immediately.

## Fix round 3 — 2026-09-20
Addresses `exec/KS2/E6.1-fix2-rereview.md` (verdict "open — drain pendingReopen in closeAll"), the one residual
gap in round 2's veto+disconnect fix: N1, N2 and the two javadoc items were all confirmed ADDRESSED. Status after
this round: **DONE**.

### The gap
`InventoryService.onPreClear()`/`onShutdown()` called `tracker.closeAll(reason)`, which only iterates the
tracker's own tracked-menu map. A vetoed close (`MenuListener`'s veto branch) untracks the player BEFORE calling
`recordPendingReopen` — so a player sitting in that next-tick veto→reopen window is, at that moment, tracked
nowhere. A reload or shutdown landing inside that window therefore neither reopened the menu nor returned the
held items — `tracker.closeAll` never saw the player, and nothing else drained `pendingReopen`.

### Fix
- `InventoryService`: new `public void closeAll(CloseReason reason)` — sweeps `tracker.closeAll(reason)` as
  before, then drains `pendingReopen`: for each entry, `consumePendingReopen` (atomic remove, so a late reopen
  task or `onQuit` racing in afterward finds nothing and no-ops), resolves the player via `Bukkit.getPlayer(uuid)`
  (skips if offline, matching `DefaultOpenMenuTracker.closeAll`'s own defensive null-check), and calls
  `menu.close(player, reason)` — the same guarded (`skipIfSlotEmpty=true`) held-item return every other
  `close(player, reason)` caller already gets, no bespoke return path.
- `onPreClear()`/`onShutdown()` now call this new `closeAll(reason)` instead of `tracker.closeAll(reason)` directly.
