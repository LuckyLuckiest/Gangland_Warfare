# WS8 grappling hook — manual client checklist (G-final)

A console-only smoke run (`grapple-boot`, see `G4-report.md`) proves the module boots and the command tree
resolves cleanly, but nothing about the actual cast/pull/fall-damage cycle — that needs a real Minecraft client
connected to `E:\Documents\Minecraft\Test Server`. This checklist is the item list from the Opus G2+G3 review's
"Cannot verify" and "Notes" sections (`exec/WS8/G2-G3-review.md`), reproduced here as concrete steps with expected
outcomes. Run with `/glw grapple give grapple 1` to obtain the item, then work down the list. Tick each row and
note anything unexpected in a new row underneath rather than editing an existing one.

## Setup

1. Deploy Gangland 0.9.2 (core jar + `gangland-gadget-0.9.2.jar`) to the test server, `/glw grapple give grapple 1`
   to obtain a hook.
2. Repeat the whole matrix once on the oldest supported build (Spigot/Paper **1.16.5**) and once on the newest
   supported build the server has (**1.21.11** per this reactor's compile target) — row 1 below is specifically
   about confirming behaviour is identical across both; every other row only needs the newest build unless it
   fails, in which case re-check on 1.16.5 too.

## Checklist

| # | Check | Steps | Expected |
|---|---|---|---|
| 1 | `PlayerFishEvent.State.IN_GROUND` fires identically on 1.16.5 and the newest build | Cast the grapple at a nearby wall on both server versions | Hook lands, `IN_GROUND` fires, pull starts, on both versions — no version-specific silent failure (research in `G4-report.md`/`G2-G3-report.md` found no API difference in the `State` enum itself between these versions, but the review flagged the live behaviour as unverified) |
| 2 | Vanilla fishing is untouched | Equip a **plain, un-tagged** fishing rod (not a grapple item) and fish normally in water | Ordinary catch/reel-in behaviour, completely unaffected — no grapple logic runs (`GrappleLaunchListener` early-returns on `Grapple.getGrappleId(item) == null`) |
| 3 | Beyond-`Max_Distance` is refused | Cast at a block further than `Max_Distance` (25 by default) — e.g. off a tall tower at distant terrain | No pull starts; `Grapple_Blocked` message received; no movement |
| 4 | A far anchor does not force-generate chunks | Cast at a block in an unloaded/ungenerated chunk far from spawn (need `Max_Distance` raised in `items/grapples.yml` for this one, or a suitably close unloaded chunk edge) | No new chunk is generated by the mere act of the pull ticking (F2 fix: `World#isChunkLoaded` only checks, never loads) — watch server chunk-count/TPS, or check for new region files, for evidence nothing was force-generated |
| 5 | No "moved too quickly" kick | Grapple pull at `Max_Pull_Speed` (1.8 by default) repeatedly, including toward a nearby anchor (fast acceleration) | Spigot/Paper's anti-cheat movement checks do not kick or rubber-band the player during a pull — if this fails, `Max_Pull_Speed`/`Pull_Acceleration` need lowering or the server's movement-check leniency needs raising |
| 6 | Grapple into a ceiling/wall (direct hit) | Cast straight up at a ceiling, or straight ahead at a nearby wall, close enough that the hook lands almost immediately | Pull starts and ends almost immediately (short `Arrival_Distance`-bounded pull into the surface); confirm no exception in console and no player getting stuck inside a block |
| 7 | Elytra `FLY_INTO_WALL`-equivalent mid-pull is **not** graced (W34 ruling a) | While gliding or moving fast toward a wall during an active pull, cause a wall-collision stop mid-pull (not the pull's own natural arrival) | Any fall/collision damage from that mid-pull collision is **not** cancelled by the landing grace — the grace only covers the landing that *ends* a pull (arrival/timeout/cancel), never a collision *during* one. Confirm this matches the documented ruling, don't treat it as a bug if it hurts |
| 8 | Sneak-cancel high up is fatal after the grace expires (W34 ruling b) | Launch from a high point, cancel the pull mid-air (sneak) while still far above the ground, wait longer than `Fall_Damage_Grace_Ticks` (40 ticks / ~2s default) before landing | Fall damage applies normally once the grace window has expired — this is intentional anti-abuse (see `items/grapples.yml`'s comments and `documentation/migration-0.9.2.md` §8), not a bug to file |
| 9 | Cooldown blocks immediate re-launch | Launch, let the pull finish (arrival or timeout), immediately try to cast again | Refused (silently — no `Grapple_Blocked` message, since cooldown/already-active is deliberately not messaged) until `Cooldown_Seconds` (8 default) elapses |
| 10 | Cancel-on-damage mid-pull | Get hit by another player/mob while mid-pull | Pull cancels immediately, landing grace granted for the fall that follows |
| 11 | Cancel-on-teleport / world-change / death mid-pull | Trigger a teleport (command, portal) or die while mid-pull | Pull cancels cleanly in each case, no lingering session (verify with a second cast attempt afterward respecting cooldown) |
| 12 | Quit mid-pull leaves nothing behind | Start a pull, then log off before it ends, log back in | On rejoin, no leftover cooldown/grace state artificially blocks a fresh launch beyond the real `Cooldown_Seconds` window measured from the original launch (F3's `forget()` clears session/cooldown/grace together on quit — but note `forget()` clears the *cooldown too*, so a very quick quit-then-rejoin may actually let a re-launch happen sooner than `Cooldown_Seconds` would otherwise allow; this is expected per the fix, not a bug) |
| 13 | 5 simultaneous pulls (concurrency / server load) | Get 5 players pulling at once (or bot clients) | No server-side error, no TPS collapse attributable to the grapple's single shared `RepeatingTimer`, all 5 pulls behave independently and correctly |
| 14 | `/glw reload` mid-pull does not double-tick | Start a pull, run `/glw reload` while it's active, let it continue | The pull either continues cleanly or cancels cleanly — critically, velocity is **not** applied twice per tick afterward (would indicate a second `RepeatingTimer` leaked; `GrappleService.onInitialize`'s `if (tickTimer == null)` guard is the fix under test here) |

## Filing results

- Any row that fails: file it in `brainstorming/bug-docket-2026-09-06/triage/<slug>.txt` per the docket process
  (CLAUDE.md "Bug docket" section) and rebuild with `build_docket.py` — do not just note it here and move on.
  Rows 7 and 8 failing would mean the *opposite* of what's expected (grace applying where it shouldn't, or not
  expiring) — those are real bugs if seen; the fatal/un-graced outcomes themselves are NOT bugs.
- Rows that pass: no action needed beyond ticking them off in whatever tracking the session uses.
