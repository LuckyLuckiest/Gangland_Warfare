# plugin-persistence — Testing Guide

## Overview

The test suite verifies the **entire persistence layer** across 13 test classes and ~120
individual tests, all backed by real SQLite I/O or real file I/O. No external server is
required.

The test suite verifies the persistence layer in two ways:

| Test class              | What it tests                                              | Needs Bukkit? |
|-------------------------|------------------------------------------------------------|---------------|
| `SQLiteIntegrationTest` | All `Database` CRUD operations via real SQLite             | No            |
| `DatabaseHelperTest`    | `DatabaseHelper.runQueries()` lifecycle and error handling | No            |

Both test classes run **without a Bukkit / Spigot server**. `JavaPlugin` and
`DatabaseHandler` are mocked with Mockito, and a real SQLite connection is opened
against a JUnit 5 temporary directory.

For tests that exercise `DatabaseHelper.runQueriesAsync()` when the plugin is
*enabled* (the branch that calls `Bukkit.getScheduler()`), you need **MockBukkit** —
see [MockBukkit setup](#mockbukkit-setup-for-bukkit-api-tests) below.

## Running the tests

> **Always use `-am`** when targeting `plugin-persistence` directly.
>
> This project uses `${revision}` as the parent POM version (Maven CI-friendly versioning).
> If you build the module in isolation, Maven cannot resolve the parent or the sibling
> dependencies (`logger-api`, `plugin-exception`, `gangland-util`) because they are not
> published to any remote repository — they exist only as local source modules.
> The `-am` flag ("also make") compiles and installs those siblings into your local
> `.m2` cache before building `plugin-persistence`.

```bash
# Run all tests in plugin-persistence (also compiles sibling deps)
cd 'E:\Programming\java\Gangland Warfare `[Cubed-GTA recoded`]\'; mvn test -pl plugin-persistence -am

# Run a single test class
mvn test -pl plugin-persistence -am -Dtest=SQLiteIntegrationTest

# Run a single test method
mvn test -pl plugin-persistence -am -Dtest="TableIntegrationTest#validateSchema_addsNewColumn"

# Run all tests in a specific package (glob)
mvn test -pl plugin-persistence -am -Dtest="org.luckyraven.gangland.persistence.component.*"

# Skip tests during a full build
mvn clean package -DskipTests
```

## Test architecture

### Why real SQLite instead of mocks?

The user story is *"test that the database itself works normally"*. Mocking the
`Database` interface would only verify that methods are called — it would not catch
SQL typos, HikariCP misconfigurations, type-mapping bugs, or schema issues.
Using a real in-process SQLite database (via `org.xerial:sqlite-jdbc`) provides
genuine confidence that the SQL generated by `SQLite.java` is correct.

### Isolation

Each test method receives a fresh JUnit 5 `@TempDir` — a unique temporary
directory on disk. A new `SQLite` instance (with its own HikariCP pool) is created
in `@BeforeEach` and torn down in `@AfterEach`. No shared state leaks between tests.

### Mocking strategy

| Component         | How it is handled                                                         |
|-------------------|---------------------------------------------------------------------------|
| `JavaPlugin`      | `mock(JavaPlugin.class)` — `getDataFolder()` returns the `@TempDir`       |
| `DatabaseHandler` | `mock(DatabaseHandler.class)` — `getDatabase()` returns the real `SQLite` |
| Bukkit static API | Not needed for sync tests; see MockBukkit section for async               |

## MockBukkit setup (for Bukkit API tests)

MockBukkit provides a lightweight, in-process Bukkit/Spigot server that runs
during JUnit tests. It is the standard approach for testing code that calls
`Bukkit.*` static methods, registers listeners, schedules tasks, etc.

**Project homepage:** https://github.com/MockBukkit/MockBukkit

### 1. Add the dependency

MockBukkit is published to **Maven Central**. Add it as a `test`-scoped dependency
in `plugin-persistence/pom.xml` (or whichever module needs it):

```xml

<dependency>
    <groupId>io.github.mockbukkit</groupId>
    <artifactId>mockbukkit-v1.21</artifactId>
    <!-- Check https://github.com/MockBukkit/MockBukkit/releases for the latest version -->
    <version>4.3.0</version>
    <scope>test</scope>
</dependency>
```

> **Version note:** MockBukkit tracks Spigot minor versions. This project targets
> `1.21.x`, so use `mockbukkit-v1.21`. Check the releases page for the newest
> stable `4.x.x` tag.

### 2. Write a test that uses the scheduler

```java
import be.seeseemelk.mockbukkit.MockBukkit;
import be.seeseemelk.mockbukkit.MockPlugin;
import be.seeseemelk.mockbukkit.ServerMock;
import database.persistence.org.luckyraven.gangland.DatabaseHelper;
import database.persistence.org.luckyraven.gangland.DatabaseHandler;
import type.database.persistence.org.luckyraven.gangland.SQLite;
import org.junit.jupiter.api.*;
import org.junit.jupiter.api.io.TempDir;

import java.nio.file.Path;
import java.util.Collections;
import java.util.concurrent.atomic.AtomicBoolean;

import static org.junit.jupiter.api.Assertions.*;
import static org.mockito.Mockito.*;

/**
 * Example showing how to test DatabaseHelper.runQueriesAsync() with a live Bukkit scheduler.
 *
 * Add mockbukkit-v1.21 to your test dependencies before enabling this class.
 */
class DatabaseHelperAsyncTest {

	@TempDir
	Path tempDir;

	private ServerMock      server;
	private MockPlugin      mockPlugin;
	private SQLite          realDb;
	private DatabaseHandler mockHandler;
	private DatabaseHelper  helper;

	@BeforeEach
	void setUp() throws Exception {
		// Boots a mock Bukkit server in-process.
		server     = MockBukkit.mock();
		mockPlugin = MockBukkit.createMockPlugin();

		realDb = new SQLite(mockPlugin);
		realDb.initialize(Collections.emptyMap(), tempDir.resolve("async_test.db").toString());
		realDb.connect();

		realDb.table("data").createTable("id INTEGER PRIMARY KEY", "val VARCHAR(255)");

		mockHandler = mock(DatabaseHandler.class);
		when(mockHandler.getDatabase()).thenReturn(realDb);

		helper = new DatabaseHelper(mockPlugin, mockHandler);
	}

	@AfterEach
	void tearDown() {
		try {
			if (realDb.getConnection() != null) realDb.disconnect();
		} catch (Exception ignored) { }
		// Shuts down the mock server and resets all static Bukkit state.
		MockBukkit.unmock();
	}

	@Test
	void runQueriesAsync_schedulesTaskOnBukkitScheduler() throws Exception {
		AtomicBoolean invoked = new AtomicBoolean(false);

		// plugin.isEnabled() returns true inside MockBukkit by default.
		helper.runQueriesAsync(db -> invoked.set(true));

		// Advance the scheduler by one tick so the async task runs.
		server.getScheduler().performOneTick();

		assertTrue(invoked.get(), "Async lambda must execute after one scheduler tick");
	}
}
```

### 3. Key MockBukkit APIs

| API                                      | Purpose                                                            |
|------------------------------------------|--------------------------------------------------------------------|
| `MockBukkit.mock()`                      | Starts the mock server; returns a `ServerMock`                     |
| `MockBukkit.unmock()`                    | Shuts down and resets everything — **always call in `@AfterEach`** |
| `MockBukkit.createMockPlugin()`          | Creates a dummy `JavaPlugin` registered with the mock server       |
| `server.getScheduler().performOneTick()` | Runs one server tick (executes scheduled sync/async tasks)         |
| `server.getScheduler().performTicks(n)`  | Runs *n* ticks                                                     |

### 4. Caveats

* `MockBukkit.mock()` / `MockBukkit.unmock()` manage **static** Bukkit state. Never
  run tests that call `MockBukkit.mock()` in parallel (use
  `@Execution(ExecutionMode.SAME_THREAD)` on the test class if needed).
* MockBukkit does not implement every Bukkit API. Missing methods throw
  `UnimplementedOperationException` — either mock them manually or open an issue
  on the MockBukkit repository.
* For Citizens NPC tests, a separate Citizens test harness would be needed;
  MockBukkit alone does not mock the Citizens API.

## Adding MySQL integration tests

MySQL tests require a running server and are therefore excluded from the default
Surefire run. The recommended pattern:

1. Use the **Testcontainers** library (`org.testcontainers:mysql`) to spin up a
   Docker-based MySQL instance automatically.
2. Tag those tests with `@Tag("mysql-integration")`.
3. Activate them only in CI with a dedicated Maven profile:

```xml
<!-- In plugin-persistence/pom.xml -->
<profiles>
    <profile>
        <id>mysql-integration</id>
        <build>
            <plugins>
                <plugin>
                    <groupId>org.apache.maven.plugins</groupId>
                    <artifactId>maven-surefire-plugin</artifactId>
                    <configuration>
                        <groups>mysql-integration</groups>
                    </configuration>
                </plugin>
            </plugins>
        </build>
        <dependencies>
            <dependency>
                <groupId>org.testcontainers</groupId>
                <artifactId>mysql</artifactId>
                <version>1.20.4</version>
                <scope>test</scope>
            </dependency>
        </dependencies>
    </profile>
</profiles>
```

Run them with:

```bash
mvn test -pl plugin-persistence -Pmysql-integration
```
